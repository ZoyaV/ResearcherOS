Hypothesis tree: from problem to experiment

Lesson~20 minscientific method

In short: what to do

  1. If research code exists, place its repository beside ResearcherOS. See how to install ResearcherOS beside your code.
  2. Ask the AI assistant to run project onboarding (koi-project-onboard). It reviews code and literature, then asks one question at a time.
  3. Answer and approve the wording. The assistant records problem → cause → expected evidence or intervention → method.
  4. Open the tree and verify that the chain represents your specification, then continue to Experiment specification.

Science combines observation, experimentation, modeling, induction, deduction, and hypothesis testing in different ways; there is no single method shared identically by every science.

ResearcherOS adopts one practical framework: critical hypothesis testing close to Karl Popper's falsificationism. State an explanation so it can be tested and potentially refuted: “we observe X; propose cause Y; if Y is true, expect Z; test it with method M.”

A successful test does not prove a hypothesis permanently; it provides grounds for provisional support. An unexpected result may reflect the hypothesis, auxiliary assumptions, measurement, or experiment design. This is a project framework, not a claim that all science must work this way. See the Stanford Encyclopedia of Philosophy entries on Scientific Method and Karl Popper.

1. Scientific method in ResearcherOS

Research is stored as a tree of linked claims. The root records the problem. Proposed causes branch from it, followed by expected evidence or interventions, then methods and individual experiments. Branches test competing explanations without merging them into one conclusion.

flowchart TD
  P[Problem] --> C1[Proposed cause]
  P --> C2[Another proposed cause]
  C1 --> E[Expected evidence]
  C1 --> R[Intervention]
  E --> M1[Test method]
  R --> M2[Test method]
  M1 --> X1[Experiment]
  M2 --> X2[Experiment]
  X1 --> V[Working verdict on cause]
  X2 -. considered with evidence .-> V
ConceptRole in research
ProblemAn observed phenomenon or practical difficulty to explain or remove. Type: problem.
CauseA testable claim about the mechanism producing the problem. The working verdict belongs here. Type: cause.
Expected evidenceAn observation expected if the proposed cause is true. Type: cause_evidence.
InterventionA system change expected to reduce the problem if the causal account is right. Failure alone does not refute the cause. Type: remediation.
MethodA protocol defining changes, controls, measurements, and the interpretation rule. Type: method.
ExperimentOne run or analysis represented by a board card.
VerdictThe cause is provisionally supported, refuted by the current test, or open; this is not final proof.

Evidence for a cause and the result of an intervention answer different questions. A helpful intervention supports its utility. Judging the cause itself requires direct evidence and tests of auxiliary assumptions.

2. How onboarding builds the tree

koi-project-onboard is for a repository that has code but no research tree. It does not invent a specification from one description or write files without researcher approval.

The assistant first studies what the code solves, what experiments change, and which checks already run. It then reviews related work, conducts a layered scientific dialogue, and asks one question at a time. A research program is an optional organizational group for projects sharing a long-term theme; it is not part of the causal branch.

flowchart TD
  A[Code repository] --> B[Review code]
  B --> C[Review literature]
  C --> D[Problem]
  D --> E[Program membership, if any]
  E --> F[Proposed cause]
  F --> G[Expected evidence or intervention]
  G --> H[Method]
  H --> I[Clarity check]
  I --> J[Researcher approval]
  J --> K[Write tree]

For every cause, the assistant asks which result would make you abandon the explanation. For a method, it records comparison, control, primary metric, and decision rule. Short titles are checked from the viewpoint of a reader unfamiliar with the project.

3. Example: researching an ARC-AGI-3 agent

ARC-AGI-3 evaluates programs that explore interactive environments and choose actions without explicit instructions. A program must infer the goal, model the environment, and plan. The official score considers goal completion and action count; 100% means solving every task at least as efficiently as humans. The technical report stated that frontier models scored below 1% at launch in March 2026.

The benchmark defines a domain and evaluation, not a ready-made project problem. The researcher must choose which gap to explain and which claim to test.

One possible branch focuses on inefficient learning in a new environment under a limited action budget. It is an example specification, not an established explanation of ARC-AGI-3 results.

Problem

Agents learn new environments inefficiently

Without instructions, agents use more actions than humans and reach goals less often.

Proposed cause

Agents fail to build a stable environment model

The agent may not connect observations and actions into a model that predicts transitions, goals, and consequences.

Expected evidence

Transition predictions disagree with observations

If the cause is correct, next-state predictions after known actions will be systematically wrong, and prediction quality should correlate with success.

Evidence method

Compare transition predictions with observations

On recorded sequences, the agent predicts the next state before its prediction is compared with the actual environment state.

Intervention

Update an explicit world model after actions

After each action, store the state, action, and observed transition, then correct the environment model.

Intervention method

Compare agents with and without a world model

Run equally configured copies on the same unseen environments with reset memory, equal action budgets, and matched random conditions. Compare environments solved and actions relative to humans. Improvement supports the intervention; no improvement does not automatically refute the cause until model quality and other assumptions are checked.
