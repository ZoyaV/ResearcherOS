Running an experiment

Lesson~15 minafter specification

The specification is ready. Now run the card and monitor progress on the tree.

In short: what to do

  1. Copy the card report path from the method board.
  2. Paste it into the assistant chat with one of the prompts below.
  3. Watch the card column and live window (the magnifier beside the method). During a run, intervene only when asked or when there is a clear failure.

Short run:

Execute the card at:
<paste path>

Use koi-execute-card: move it to in progress immediately, follow the subtasks, and finish in done.

Long or remote run:

Run systematic research for this card:
<paste path>

Use koi-card-autoresearch: Manager → Researcher → Debugger.

1. Choose a workflow

Both workflows operate on one method-board card. Choose by run length and monitoring needs.

Card executionAutoresearch
Workflowkoi-execute-cardkoi-card-autoresearch
WhenMinutes to hours in one session; local or short runHours to days; remote job requiring monitoring and failure triage
WhoOne assistant handles execution, edits, and reportManager, Researcher, and Debugger roles
Prompt“Execute the card…”“Run systematic research for the card…”

Autoresearch does not replace card execution. Kanban status, report subtasks, and done status still follow koi-execute-card; autoresearch adds roles and a monitoring cadence.

2. Short run: card execution

koi-execute-card keeps card status and report checkboxes synchronized with actual work, not updated cosmetically at the end.

flowchart TD
  A[Find card] --> B[Backlog → in progress immediately]
  B --> C[Read specification and subtasks]
  C --> D[Run experiment subtasks]
  D --> E[Check off work in report]
  E --> F[Record results]
  F --> G[Move to done]
  G --> H[Formulate finding]
  1. First action: in progress. Move the backlog card before reading the report or running code.
  2. During work: check §3. Mark and save each subtask as soon as its criterion is met; do not batch checkmarks at the end.
  3. Results go in §4 and later. Add promised tables and charts, or explicitly state why an item was not completed.
  4. Last action: done. Move the card only after all subtasks and conclusions are recorded, before replying to the user and extracting the finding.
Execute card <title or id> in project <project> end to end:
move it to in progress, run every subtask, update progress as you work,
then mark it done and record the finding.

While the card is running, the method's live window can show a log tail, metrics directory, and short progress note through live_log, metrics_dir, and live_note. The UI reads these from disk.

3. Long run: autoresearch

koi-card-autoresearch separates ownership for a long or remote job: one role initializes the card, one operates and monitors it, and one diagnoses failures without silently editing code.

RoleDoesDoes not
ManagerOnce: card to in progress, live-window fields, state file, handoffRun training or fix code
ResearcherStart the job, monitor it, update §3, call Debugger, finish the cardChange someone else's code without explicit approval
DebuggerRead logs and resource monitoring; write a recommendation to stateEdit files or restart the job
flowchart TD
  U[User request] --> M[Manager: in progress + live window + state]
  M --> R[Researcher: start job]
  R --> W[Monitor frequently, then less often]
  R --> D[Debugger: scheduled triage]
  W -->|failure| I[Call Debugger]
  I --> D
  D -->|recommendation in state| W
  W -->|complete| F[Report + done + finding]

Default cadence: Manager once; Researcher every minute for 20 checks, then every 20 minutes; Debugger at startup, every 10 minutes, and on demand. Early failures are handled immediately.

A small JSON state file such as state/<project>-<card>.json records job status, the Researcher's last check, and pending Debugger advice. Project-specific launch scripts, remote hosts, and GPU monitoring belong in a project skill beside the experiment code. Without one, the Researcher maintains the cadence manually.

One autoresearch run must not cover two cards. The Debugger must not edit code or restart jobs, the Manager must not launch training, and a card must not reach done with unchecked subtasks unless the report explicitly records the omission.

4. After done

  1. Human-readable finding: koi-done-research saves a clear question and answer, with technical figures separated.
  2. Results review: koi-report-review verifies that tables and conclusions match the specification.
  3. Synchronization: koi-project-sync sends research materials to the repository when needed.
