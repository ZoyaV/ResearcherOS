Experiment specification

Lesson ~10 min before execution

A good specification answers three questions in advance: what are we testing, how will we test it, and which result determines the decision?

In short: what to do

  1. Describe the research assumption in one or two sentences.
  2. Run the experiment-design workflow (koi-grill-experiment): it asks questions and builds a draft card.
  3. Run the specification-review workflow (koi-report-review): three independent checks assess the prose, completeness, and subtasks.
  4. Open the card in the board backlog. Correct inaccuracies manually or ask the assistant to edit them.
  5. Repeat any failed checks. Move the card to in progress only after they pass.

1. Typical workflow

Start by giving the assistant a short draft. It does not need perfect wording; the workflow asks questions and helps refine it. 

For method <name> in project <name>,
I want to test: <research assumption>.

Build the specification with koi-grill-experiment,
then review it with koi-report-review.
Ask one question at a time. Do not run anything yet.

After the interview, read the title, description, and first three report sections. If something is wrong, fix it or ask the assistant: “Correct <specific issue> and repeat the failed checks.”

2. Supporting workflows

Workflow What it does
koi-grill-experiment Asks one question at a time and prepares a card plus the first three report sections. Runs nothing.
koi-report-review Separately checks prose clarity, specification completeness, and subtask quality. Checks repeat after edits.
koi-prose-style Shortens and clarifies titles, descriptions, tree nodes, and findings. Useful throughout the project.

How the prose workflow improves text

Before

“The approach represents a groundbreaking shift in the agent's ability to generalize.”

After

“With the world model, the agent solved 12 environments instead of 8.”

Rewrite the card title and description with
koi-prose-style. Preserve the facts and remove
bureaucratic language and internal jargon.

3. Experiment or engineering task

An experiment answers a research question. It may require code changes, but code is a means; the primary result is data, tables, charts, and a finding.

An engineering task changes the system. Its primary result is code whose correctness is demonstrated by tests.

Experiment Engineering task
Goal Test an assumption. Implement behavior.
Result Data and a finding. Code and tests.
Done The protocol is complete and a verdict recorded. Tests demonstrate the requirements.

Testing an assumption can include both development and experimentation. Sometimes you must add a capability before measuring its effect. Mark such a card with feature, experiment, or both.

If implementation and measurement fit in one small iteration, define separate done criteria for code and the research finding. If implementation requires its own validation, create two cards: engineering first, experiment second.

Scope of one card

One card is one iteration. If an experiment cannot end in one verdict, or a task in one set of checks, reduce its scope.

SMART for one card

SSpecific action.
MMeasurable result.
AAchievable, limited scope.
RRelated to a tree node.
TTask order and dependencies.

This is an internal ResearcherOS check called SMART. Here, T means task order and dependencies rather than the standard SMART criterion.

Ready-specification checklist

  1. The card's output is clear: code, a research finding, or both; each has its own done criterion.
  2. The experiment has one primary measurable indicator and a predefined decision rule.
  3. An engineering task states the required behavior and tests.
  4. Dependencies and out-of-scope work are listed.
  5. Every subtask produces a verifiable result.
  6. The title is short; details live in the description and report.
Weak subtask

“Run experiments and look at the results.”

Verifiable subtask

“On 20 environments not used during development, compare the agent with and without a world model: run each condition five times, save raw metrics, and complete the summary table.”
