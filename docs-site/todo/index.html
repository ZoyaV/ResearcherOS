01 · Сравнение

Сравнение Cloud / Local архитектуры

Текущая работает так-то

Сейчас ResearcherOS — это локальное приложение поверх проекта. Исследователь и агент работают рядом с кодом и читают/изменяют исследовательское состояние в файлах репозитория: дерево гипотез, эксперименты, отчёты, знания и статью. Git хранит историю, ветки и перенос состояния между копиями. Hub получает опубликованный снимок и показывает его для чтения, но не владеет исходным проектом.

Возможная реализация по примеру Linear

Cloud-версия может выглядеть как единое рабочее пространство, где исследовательское состояние живёт внутри сервиса, а не в локальной копии репозитория. Входная точка — Organization, внутри неё Teams и Projects; проект содержит общие объекты ResearcherOS: hypotheses, experiments, reports, knowledge и papers. Каждый объект получает владельца, статус, историю изменений, комментарии и права доступа. Пользователь видит одно актуальное состояние, а агент подключается к тому же проекту как участник — через Agent API или MCP — и может выполнять ограниченные операции от своего имени.

По аналогии с Linear, где рядом с рабочими объектами есть Activity, Reviews и агентские действия, в ResearcherOS стоит выделить отдельные AgentRun / Session: кто запустил, что агент прочитал, какие tools вызвал, какие артефакты создал и где требуется решение человека. Git при этом можно оставить интеграцией — для кода, export, импорта и привычного versioned checkpoint, но не единственным источником shared state.

Образ идеала: ResearchState остаётся узлом правды

Идеальная версия может быть гибридной: Cloud отвечает за совместную работу и скорость интерфейса, но каноническое состояние исследования по-прежнему живёт в Git. Cloud хранит проекцию для realtime, поиска и уведомлений; окончательная запись проходит через доменные операции, валидацию и коммит в репозиторий.

UI / Agent API / MCP→ResearcherOS mutation service→validate → Git commit→ResearchState

Как это сделать. У каждого Cloud Project есть привязанный Git remote и каноническая ветка ResearchState. Пользователь или агент не меняет базу напрямую: он отправляет операцию — например, «создать Experiment» или «добавить вывод в Report». Сервис проверяет права и инварианты, применяет изменение к рабочему дереву, создаёт коммит и публикует событие. UI сразу получает optimistic update, а затем подтверждение commit SHA. Если одновременно пришли две операции, сервер ставит их в очередь или создаёт понятный конфликт для ревью — Git остаётся механизмом разрешения, истории и rollback.

Главный trade-off: текущая архитектура делегирует инфраструктурную сложность Git. Cloud-архитектура забирает эту сложность внутрь ResearcherOS в обмен на контроль над collaboration, agents и shared state.

Оценка решения

Cloud / Local: цена выбора

Если идти в Cloud

Потребуется больше продукта и эксплуатации

  • Больше времени на реализацию и тестирование. Нужно построить не только UI, но и auth, multi-tenancy, API, очереди, realtime, миграции, backup и сценарии восстановления.
  • Постоянная поддержка сервиса. Кто-то должен следить за доступностью, обновлениями, безопасностью, логами, стоимостью инфраструктуры и инцидентами.
  • Сложнее обеспечить корректность. Придётся тестировать права доступа, конкурентные изменения, повторную доставку событий, идемпотентность и рассинхронизацию проекций.
  • Дороже первый запуск и миграция. Нужно определить cloud-модель данных, перенести проекты и сохранить экспорт обратно в понятный Git-формат.
  • Зависимость от сети и сервиса. Без доступного backend shared experience ухудшается; нужен продуманный offline/export fallback.

Если оставаться Local / Git-centric

Сохраняется простота, но растёт трение

  • Более сложные пайплайны синхронизации. Нужно отдельно поддерживать push/pull, ветки, конфликты, публикацию снимков и realtime-слой — хотя эти процессы потенциально можно улучшать.
  • Менее удобно для команды. У людей остаются отдельные копии, нужно понимать Git-контекст, ждать синхронизации и разбираться, какая версия состояния актуальна.
  • Слабее общий контекст для агентов. Агенту приходится одновременно работать с локальной файловой системой, Git и отдельными API; подключение удалённого агента получается неестественным.
  • Сложнее масштабировать collaboration. Чем больше участников и параллельных действий, тем заметнее ограничения branch/merge-модели для живого исследовательского состояния.
  • Стратегический риск. Кто-то может раньше реализовать удобную cloud-архитектуру для shared research state — и тогда ResearcherOS будет сложнее конкурировать за командный UX.

02 · Приобретём

Что с ней приобретём

  • Multi-user UX. Все смотрят на один Experiment, Kanban или Hypothesis Tree.
  • Agent interoperability. MCP становится стабильным контрактом для Claude, Codex, OpenCode и custom agents.
  • First-class lifecycle. У эксперимента появляются отдельные AgentRun, статусы, активности и артефакты.
  • Fine-grained permissions. Разные scopes для людей, команд и агентов.
  • Асинхронность и наблюдаемость. Webhooks, event bus, audit и долгие запуски работают как часть платформы.
  • Централизованный retrieval. Единый search/index поверх hypotheses, reports, knowledge и experiments.

03 · Потеряем

Что с ней потеряем

  • Бесплатную силу Git. Organization, Team, Project, RBAC, fork, revert и review становятся нашей задачей.
  • Простоту multi-tenancy. Нужна изоляция tenant на каждом API endpoint.
  • Portability. Состояние в Cloud DB уже не равно набору Markdown-файлов.
  • Прямую связь code ↔ research state. Агент работает через filesystem/Git и MCP как через две среды.
  • Offline-first. Shared cloud state требует доступности сервиса.
  • Операционную лёгкость. Появляются auth, migrations, storage, queue, backup, monitoring и concurrency control.

02 · UI / UX дизайн

Проработать User Experience

Сделать ResearcherOS удобным инструментом ежедневной работы, а не только выразительной демонстрацией возможностей.

01

Переработка дизайна

Снизить визуальную нагрузку и сделать интерфейс спокойнее: иерархия, плотность, контраст, типографика, состояния загрузки и ошибки.

Отдельно проработать human-in-the-loop: где агент предлагает, где человек подтверждает, что можно откатить, как видно pending changes, историю и запрос на решение.

Результат: несколько тем интерфейса — более выразительная и менее контрастная — с единой системой компонентов.

02

Прототипирование сценариев

До реализации проверить ключевые потоки: постановка гипотезы, запуск эксперимента, разбор отчёта, предложение правки агентом и ручное подтверждение.

Для каждого сценария описать happy path, отмену, ошибку, ожидание долгого запуска и переход между человеком и агентом.

Результат: кликабельные прототипы и набор UX-критериев, по которым можно сравнивать варианты.

03

A/B-тестирование

В идеале — сравнить текущий и обновлённый интерфейс на одинаковых задачах и реальных рабочих сценариях.

Измерять не только «нравится / не нравится», но и время до результата, число ошибок, число отмен, понятность статуса агента и долю действий, завершённых без подсказки.

Результат: решение, какие изменения оставить, на основе наблюдений и метрик, а не вкусов.

03 · Skills

Доработка и тестирование скилов

Сделать skills воспроизводимыми процедурами, а не набором удачных промптов.

Что нужно проработать

Проверить, какие skills действительно помогают в исследовательском цикле, где они дублируют друг друга и какие решения должны оставаться за человеком.

  • Аудит каталога: назначение, входы, выходы, ограничения и ожидаемый результат каждого skill.
  • Контракты: единый формат контекста, артефактов, статусов, ошибок и human review.
  • Тестовые сценарии: нормальные данные, неполный контекст, конфликтующие требования, повторный запуск и отказ внешнего инструмента.
  • Регрессионный набор: фиксированные проекты и задачи, на которых проверяется качество после изменения skill или модели.
  • Делегация с осторожностью: отдельные skills можно отдавать на внешнюю разработку только вместе с тестами, критериями приёмки и владельцем внутри ResearcherOS.

04 · Методические материалы

Уроки и документация

Объяснить не только кнопки, но и правильную модель исследовательской работы.

Уроки

Пошаговые сценарии: от гипотезы к эксперименту, от запуска к отчёту, от отчёта к знанию и следующему решению.

Документация

Архитектура, формат проекта, API, skills, роли человека и агента, синхронизация, восстановление и ограничения.

Примеры и шаблоны

Минимальные рабочие проекты, хорошие и плохие примеры постановок, чеклисты ревью и шаблоны для новых команд.

Критерий готовности. Новый пользователь должен пройти основной исследовательский цикл без устного объяснения команды, а разработчик — понять контракт функции по документации и воспроизводимому примеру.

05 · Тестирование платформы

Проверить надёжность целиком

Тестировать не только отдельные функции, но и путь от действия пользователя или агента до сохранённого исследовательского результата.

01

Функциональный слой

Unit- и integration-тесты API, файловых форматов, доменных правил, Git-синхронизации, proposal/review и прав доступа.

02

Пользовательские сценарии

E2E-проверки основных путей в UI: создание проекта, гипотеза, эксперимент, агентский запуск, отчёт, ручное подтверждение и откат.

03

Сложные условия

Конкурентные изменения, потеря сети, долгие запуски, частично записанные результаты, большие проекты, разные браузеры и повторная доставка событий.

04

Качество релиза

Smoke-тест после деплоя, регрессия перед релизом, мониторинг ошибок, проверка миграций и понятный rollback-план.

Предложение. Завести небольшой постоянный набор «golden projects» — эталонных проектов с ожидаемыми состояниями и действиями. Прогонять его на каждом изменении платформы, UI и skills, чтобы видеть, не сломался ли полный исследовательский цикл.

06 · Спецификация проекта

Сделать проект безопасным для контрибьюций

Описать систему так, чтобы новые люди и агенты могли добавлять возможности, понимать границы изменений и не ломать существующие сценарии.

Спецификация как контракт

Документ должен быть не только справкой, но и рабочим соглашением между авторами проекта, UI, backend, skills и агентами.

  • Карта системы: слои, зависимости, source of truth, границы локального приложения, Hub и будущего Cloud.
  • Доменные контракты: форматы ResearchState, project metadata, reports, papers, skills, API-операций и событий.
  • Правила расширения: куда добавлять новую фичу, UI-компонент, skill, виджет, интеграцию или миграцию.
  • Инварианты и совместимость: что нельзя менять без миграции, как версионировать схемы и как поддерживать старые проекты.
  • Протокол изменения: issue → proposal/design note → реализация → тесты → документация → review → release note.
  • Инструкции для агентов: разрешённые операции, обязательное чтение контекста, критерии остановки и запрет на незаметные обходы контрактов.
  • Definition of done: изменение принято только когда есть код, тест, документация, пример использования и понятный rollback.
Результат. Один источник правил для контрибьюторов: новый участник понимает, как устроен проект и как внести изменение; агент может проверить себя до и после работы; ревьюер видит, какие контракты затронуты и почему изменение безопасно.
